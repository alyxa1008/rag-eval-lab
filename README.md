# rag-eval-lab

한국어 ESG 보고서(PDF)를 대상으로 하이브리드 검색(벡터 + BM25)의 품질을 **숫자로** 평가하는 프로젝트입니다.

## 문제 정의

이전에 대학 상담 RAG 챗봇을 만들어 운영하면서 세 가지 한계가 있었습니다.

- 튜닝과 검증에 같은 질의 세트를 써서 held-out이 없었다.
- 벡터 60% + BM25 40% 비율을 다른 비율과 비교하지 않고 채택했다.
- 검색 품질을 Recall@k 같은 지표로 재지 않았다.

이 저장소는 그 세 가지를 직접 해보고, "held-out 세트에서 Recall@5가 몇 %였다"를 말할 수 있게 만드는 것이 목표입니다.

**결론 (heldout 10문항, 1회 실행):** 청크 1500자 + 벡터 0.6 : BM25 0.4 하이브리드에서 Recall@1 0.90, Recall@5 1.00, MRR 0.95. 자세한 표는 [결과](#결과-dev-30문항-쪽-단위-적중) 참고.

## 파이프라인

| 단계 | 방법 |
|---|---|
| 파싱 | PyMuPDF(본문) + pdfplumber(테두리 있는 표) + 단어 좌표 기반 재구성(테두리 없는 숫자 표). 표는 행 단위로 `항목 \| 단위 \| 2022년: x \| 2023년: y` 형태로 텍스트화하고 N행마다 분할 |
| 청킹 | 페이지 기준 텍스트 청크 + 표 청크 분리. 모든 청크에 `page` 메타데이터 |
| 임베딩 | BAAI/bge-m3 로컬 실행 (sentence-transformers), 결과 SQLite 캐시. 설정으로 OpenAI text-embedding-3-small 전환 가능 |
| 벡터 DB | ChromaDB (로컬) |
| 키워드 검색 | rank_bm25 + kiwipiepy 형태소 분석 |
| 융합 | min-max 정규화 후 `w*vector + (1-w)*bm25` |
| 리랭커 (선택) | BAAI/bge-reranker-v2-m3 (sentence-transformers CrossEncoder), 융합 상위 20개만 재정렬 |

## 평가셋

- `data/eval_set.csv`, 40문항(number 15 / table 8 / text 12 / multi 5). **질문 초안은 AI 도구로 만들고, 정답과 `gold_pages`는 제가 원문과 대조해 검수했습니다.** 유형 배분, 문서 표현을 베끼지 않는 바꿔 쓰기 원칙, 시드 고정 무작위 heldout 추출은 제가 정한 기준입니다.
- 컬럼: `id, question, answer, gold_pages, type, split`
- 40문항 중 10개(25%)를 시드 고정 무작위 추출로 `heldout`에 배정했고, 튜닝 중에는 보지 않습니다. heldout은 `--split heldout`을 명시해야만 실행됩니다.

## 지표

- Recall@k (k=1,3,5): 상위 k개 청크 중 `gold_pages`에 속한 청크가 하나라도 있으면 성공
- MRR: 처음 맞춘 청크의 순위 역수 평균
- type별(number / table / text / multi) 분해

## 실행

```bash
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt && pip install -e .
cp .env.example .env            # OpenAI 임베딩을 쓸 때만 OPENAI_API_KEY 입력 (기본은 로컬 bge-m3, 키 불필요)

# M0: 파싱 결과 확인 (페이지별 글자 수·표 수·표 행 수)
python -m rag_eval parse --config configs/base.yaml
python -m rag_eval parse --config configs/base.yaml --page 12   # 특정 쪽 청크 전문 보기

# M1: 인덱싱(파싱 → 임베딩(캐시) → ChromaDB) 후 단건 검색
python -m rag_eval index --config configs/base.yaml
python -m rag_eval search --config configs/base.yaml -q "2024년 Scope 1 온실가스 배출량"
python -m rag_eval search --config configs/base.yaml -q "임직원 수" --mode bm25   # API 키 없이 BM25만
python -m rag_eval search --config configs/base.yaml -q "임직원 수" -w 0.3        # 벡터 가중치 지정

# 평가셋 형식 검사
python -m rag_eval check-eval-set

# M2: 평가 (기본은 dev 세트만. heldout은 설정 확정 후 마지막에 딱 한 번)
python -m rag_eval run --config configs/base.yaml
python -m rag_eval run --config configs/base.yaml -w 0.3          # 가중치만 바꿔서 실행
python -m rag_eval run --config configs/base.yaml --split heldout  # 최종 1회
# -> results/<config>/<split>/<run>/ 에 per_query.csv, summary.csv, summary.md, run_info.json

# M3: 실험 (전부 dev만)
python -m rag_eval sweep --config configs/base.yaml              # w = 0 / 0.3 / 0.5 / 0.6 / 0.7 / 1.0
python -m rag_eval sweep --config configs/base.yaml --rerank     # + bge-reranker-v2-m3
python -m rag_eval index --config configs/chunk400.yaml && python -m rag_eval sweep --config configs/chunk400.yaml
python -m rag_eval compare                                        # results/compare_dev.md 한 표로 모음
python -m rag_eval answer-hit --split dev                         # 청크 안 정답 포함 여부로 재채점 (검색 재실행 없음)
python -m rag_eval ci --split dev                                 # 부트스트랩 95% 신뢰구간, 기준 대비 쌍 차이

pytest
```

## 결과 (dev 30문항, 쪽 단위 적중)

모든 수치는 `results/` 아래 CSV에서 그대로 옮긴 것이다. 재현: `python -m rag_eval sweep --config configs/<name>.yaml [--rerank]`, 비교표: `python -m rag_eval compare`.

### 실험 1. 융합 가중치 w (청크 800자, 리랭커 off)

`score = w × vector(bge-m3) + (1-w) × BM25(kiwi)`

| w | Recall@1 | Recall@3 | Recall@5 | MRR | number R@1 | table R@1 | text R@1 | multi R@1 |
|---|---|---|---|---|---|---|---|---|
| 0 (BM25만) | 0.833 | 0.867 | 0.933 | 0.865 | 0.667 | 0.667 | 1.000 | 1.000 |
| 0.3 | 0.833 | 0.933 | 1.000 | 0.894 | 0.667 | 0.667 | 1.000 | 1.000 |
| 0.5 | 0.933 | 1.000 | 1.000 | 0.956 | 0.889 | 0.833 | 1.000 | 1.000 |
| **0.6** | **0.967** | 1.000 | 1.000 | 0.978 | 0.889 | 1.000 | 1.000 | 1.000 |
| **0.7** | **0.967** | 1.000 | 1.000 | **0.983** | 0.889 | 1.000 | 1.000 | 1.000 |
| 1.0 (벡터만) | 0.900 | 1.000 | 1.000 | 0.944 | 0.889 | 1.000 | 0.909 | 0.750 |

- BM25만 쓰면 숫자·표 질문의 1위 적중이 67%에 그친다. 벡터만 쓰면 반대로 서술형·여러 쪽 질문이 약해진다.
- 두 점수를 섞으면 어느 한쪽보다 좋고, w=0.5~0.7 구간이 평탄한 최적 구간이다. 이전 프로젝트에서 비교 없이 썼던 0.6은 이 구간 안에 있었다.

### 실험 2. 리랭커 (BAAI/bge-reranker-v2-m3, 융합 상위 20개 재정렬, 청크 800자)

| w | 리랭커 off R@1 / MRR | 리랭커 on R@1 / MRR |
|---|---|---|
| 0 (BM25만) | 0.833 / 0.865 | **0.967 / 0.978** |
| 0.3 | 0.833 / 0.894 | 0.933 / 0.961 |
| 0.6 | 0.967 / 0.978 | 0.933 / 0.961 |
| 0.7 | **0.967 / 0.983** | 0.933 / 0.961 |
| 1.0 (벡터만) | 0.900 / 0.944 | 0.933 / 0.961 |

- 리랭커는 BM25 단독의 실패를 거의 다 복구한다(0.833 → 0.967). 1차 검색이 약할 때는 효과가 크다.
- 그러나 하이브리드(w≥0.5) 위에 얹으면 오히려 1위 적중이 1문항 줄었다. 리랭커를 켜면 w와 무관하게 결과가 거의 같아지는데, 상위 20개 후보가 비슷해서 최종 순위를 리랭커가 결정하기 때문이다.

### 실험 3. 청크 크기 (리랭커 off)

| 청크 설정 | 청크 수 | w=0 R@1 | w=0.6 R@1 / MRR | w=0.7 R@1 / MRR | w=1 R@1 |
|---|---|---|---|---|---|
| 400자 (표 5행) | 685 | 0.833 | 0.933 / 0.961 | 0.967 / 0.975 | 0.900 |
| 800자 (표 10행) | 381 | 0.833 | 0.967 / 0.978 | 0.967 / 0.983 | 0.900 |
| **1500자 (표 20행)** | 238 | 0.800 | **1.000 / 1.000** | **1.000 / 1.000** | 0.900 |

- 큰 청크가 가장 좋았다. 이 문서는 한 쪽에 표 하나가 통째로 들어가는 경우가 많아, 표가 쪼개지지 않는 쪽이 유리하다.
- 단, 지표가 쪽 단위 적중이라 청크가 커질수록 유리한 구조적 편향이 있다(한계 참고).

### 실험 4. 쪽이 아니라 청크 안에 정답이 있는가 (AnsHit@k)

쪽 단위 Recall은 청크가 클수록 유리하다. 그래서 같은 검색 결과를 **"gold 쪽의 청크이면서 그 청크 텍스트에 정답 값(숫자, 없으면 핵심 단어)이 실제로 들어 있는가"**로 다시 채점했다(`python -m rag_eval answer-hit`). 새 검색은 돌리지 않았다.

| 설정 (dev) | Page@1 | **Ans@1** | Page@3 | Ans@3 | AnsMRR |
|---|---|---|---|---|---|
| 1500자, w=0.6 (확정) | 1.000 | **0.967** | 1.000 | 1.000 | 0.983 |
| 800자, w=0.7 | 0.967 | **0.933** | 1.000 | 1.000 | 0.967 |
| 800자, w=0.6 | 0.967 | **0.933** | 1.000 | 1.000 | 0.961 |
| 400자, w=0.6 | 0.933 | **0.867** | 1.000 | 1.000 | 0.928 |
| 800자, BM25+리랭커 | 0.967 | **0.933** | 1.000 | 1.000 | 0.961 |
| 800자, w=0.6+리랭커 | 0.933 | **0.900** | 1.000 | 1.000 | 0.944 |
| 800자, 벡터만 | 0.900 | **0.867** | 1.000 | 1.000 | 0.928 |
| 800자, BM25만 | 0.833 | **0.800** | 0.867 | 0.833 | 0.838 |
| **heldout** 1500자, w=0.6 (n=10) | 0.900 | **0.900** | 1.000 | 1.000 | 0.950 |

- 청크 수준으로 바꿔도 순위는 그대로다. 1500자 청크의 우위는 "쪽을 넓게 덮어서" 생긴 착시만은 아니었다.
- 다만 1500자에서도 1문항(q025 지속가능경영위원회 설치 시기)은 쪽은 맞았지만 1위 청크에 정답 문장이 없었다. 쪽 단위 지표가 놓치는 종류의 실패다.
- heldout에서는 두 지표가 같았다(0.900).

### 통계적 유의성 (부트스트랩, dev 30문항)

질문 30개를 복원추출로 5,000번 재표본해 95% 신뢰구간을 구했고, 설정 간 차이는 같은 질문 쌍으로 계산했다(`python -m rag_eval ci`). 기준은 800자·w=0.6.

| run | n | R@1 | MRR | ΔR@1 vs ref | ΔMRR vs ref | P(ref better) |
|---|---|---|---|---|---|---|
| base:w0.6 | 30 | 0.967 [0.90, 1.00] | 0.978 [0.93, 1.00] | (reference) |  |  |
| base:w0.7 | 30 | 0.967 [0.90, 1.00] | 0.983 [0.95, 1.00] | -0.000 [-0.00, -0.00] | +0.006 [-0.00, +0.02] | 0.00 |
| base:w0.5 | 30 | 0.933 [0.83, 1.00] | 0.956 [0.89, 1.00] | -0.033 [-0.10, -0.00] | -0.022 [-0.07, -0.00] | 0.63 |
| base:w0.3 | 30 | 0.833 [0.70, 0.97] | 0.894 [0.80, 0.98] | -0.133 [-0.27, -0.03] | -0.083 [-0.17, -0.02] | 0.99 |
| base:w1 | 30 | 0.900 [0.77, 1.00] | 0.944 [0.88, 1.00] | -0.067 [-0.17, -0.00] | -0.033 [-0.08, -0.00] | 0.87 |
| base:w0 | 30 | 0.833 [0.70, 0.97] | 0.865 [0.74, 0.97] | -0.133 [-0.27, -0.03] | -0.113 [-0.22, -0.03] | 0.99 |
| base:w0.6_rerank | 30 | 0.933 [0.83, 1.00] | 0.961 [0.90, 1.00] | -0.033 [-0.10, -0.00] | -0.017 [-0.05, -0.00] | 0.63 |
| chunk400:w0.6 | 30 | 0.933 [0.83, 1.00] | 0.961 [0.90, 1.00] | -0.033 [-0.10, -0.00] | -0.017 [-0.05, -0.00] | 0.63 |
| chunk1500:w0.6 | 30 | 1.000 [1.00, 1.00] | 1.000 [1.00, 1.00] | +0.033 [-0.00, +0.10] | +0.022 [-0.00, +0.07] | 0.00 |

- **w=0.6과 0.7은 구분할 수 없다.** 1위 적중은 완전히 같고 MRR 차이 +0.006의 구간이 0을 포함한다.
- **BM25만(w=0)과 BM25 위주(w=0.3)는 유의하게 나쁘다.** 차이의 구간이 0을 포함하지 않는다(ΔR@1 −0.133 [−0.27, −0.03]).
- **벡터만, 리랭커 추가, 청크 400/1500은 기준과 유의한 차이가 없다.** 구간이 0에 닿는다. 1500자를 확정한 것은 점추정이 가장 좋아서이지, 통계적으로 우월해서가 아니다.

### 확정 설정과 heldout

dev에서 고른 설정: **청크 1500자, w=0.6, 리랭커 off** (`configs/chunk1500.yaml`). w는 0.5~0.7이 동률이라 구간 중앙값을 택했다. 부트스트랩 결과 이 선택은 800자·w=0.6/0.7과 통계적으로 구분되지 않는다(위 표).

heldout 10문항 결과 (1회 실행, `python -m rag_eval run --config configs/chunk1500.yaml --split heldout`):

| 구분 | n | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|---|
| **전체** | 10 | **0.900** | **1.000** | **1.000** | **0.950** |
| number | 6 | 1.000 | 1.000 | 1.000 | 1.000 |
| table | 2 | 0.500 | 1.000 | 1.000 | 0.750 |
| text | 1 | 1.000 | 1.000 | 1.000 | 1.000 |
| multi | 1 | 1.000 | 1.000 | 1.000 | 1.000 |

- dev에서 1.000이던 Recall@1이 heldout에서는 0.900으로, 1문항(q018 삼성 드림클래스 누적 수혜자 수)을 2위로 놓쳤다. 드림클래스를 소개하는 서술형 쪽(52쪽)이 숫자 표(63쪽)보다 위에 올랐다. dev 실패 분석에서 본 "서술문이 표 행을 밀어내는" 패턴과 같다.
- dev 수치가 heldout보다 높은 것은 dev에서 설정을 고르고 gold를 보완한 데 따른 낙관 편향으로 본다. 이 프로젝트가 말할 수 있는 최종 숫자는 **heldout Recall@1 0.90, Recall@5 1.00, MRR 0.95** 이다.

|---|---|---|

| **같은 지표의 범위별 수치가 여러 쪽에 존재** — 재생에너지 전환율이 DX만(14쪽 93.4%), DS만(25쪽 24.8%), 전사(69쪽 31.4%)로 따로 있음 | q010 재생에너지 전환율 | 800자 청크에서는 모든 설정이 2~5위. 1500자에서만 1위 |

| **의미상 가까운 다른 쪽** — CEO 메시지(4쪽)가 목표 연도와 재생에너지를 함께 언급 | q026 DX 재생에너지 100% 목표 연도 | 벡터만(w=1)에서 2위 |
| **리랭커의 서술문 선호** — 표 행 텍스트보다 같은 단어가 든 문장을 높게 평가 | q001 매출액(회사소개 쪽의 부문별 매출을 선택), q010 | 리랭커 on에서만 실패 |
| **gold 누락(평가셋 결함)** — 정답이 적힌 쪽이 더 있었음 | q003, q012, q013, q029, q030, q036, q037, q039 | 실패 분석 과정에서 발견해 gold_pages 보완 후 전부 재실행. 위 표의 수치는 보완 후 결과 |

숫자·표 질문이 BM25에 특히 약하고 벡터가 그걸 메운다는 것이 가장 분명한 패턴이었다. 이전 프로젝트에서 "숫자 질문이 자주 틀린다"고 느꼈던 것의 원인이 여기 있었을 가능성이 높다.

## 효과가 없었던 것

- **하이브리드 위의 리랭커.** w=0.6/0.7에서 리랭커를 켜면 Recall@1이 0.967 → 0.933으로 내려갔다. 1차 검색이 이미 좋을 때는 비용(질의당 20쌍 cross-encoder 추론)만 늘었다.
- **BM25 비중을 높이는 것(w=0.3).** 벡터만 쓰는 것(w=1.0)보다도 나빴다(R@1 0.833 vs 0.900). 이 문서에서는 BM25가 보조 신호일 때만 가치가 있었다.
- **작은 청크(400자).** 표가 5행 단위로 쪼개지며 800자보다 R@1·MRR이 낮거나 같았고, 청크 수는 1.8배로 늘었다.

## 한계

- **dev 30문항은 작다.** 질문 하나가 Recall 3.3%p다. 부트스트랩으로 확인한 결과 상위 설정들끼리는 유의한 차이가 없고, BM25 단독·BM25 위주만 유의하게 나쁘다.
- **Recall@3 이상은 포화됐다.** 설정 간 차이는 Recall@1과 MRR에서만 보인다. 문항을 더 어렵게(바꿔 쓰기 강화, 유사 지표 혼동 유도) 만들면 변별력이 커질 것이다.
- **쪽 단위 적중은 큰 청크에 유리하다.** 청크 안에 정답이 있는지로 다시 채점해도(실험 4) 순위는 같았지만, 생성 단계까지 평가하면 큰 청크의 비용(컨텍스트 길이, 불필요 정보)이 드러날 수 있다.
- **평가셋 질문은 AI 도구가 초안을 만들었고 검수는 내가 했다. dev 질문의 gold는 검색 결과를 본 뒤 보완했다.** 그래서 dev 수치에는 낙관 편향이 있을 수 있다. heldout 10문항의 gold는 검색 결과를 보지 않은 상태에서 정답 토큰 자동 대조로만 검수했다.
- **문서 1개(87쪽)** 결과라 다른 보고서로 일반화할 수 없다.
- 76~79쪽(제3자 인증·검증 의견서)은 스캔 이미지라 텍스트가 추출되지 않는다. OCR은 범위 밖.
- 연도 × 사업부문처럼 헤더가 2단인 표(72~74쪽)는 숫자는 추출되지만 열 이름이 연도까지만 붙는다.
- 본문 텍스트 청크에도 표 셀이 평문으로 남아 있어 표 청크와 내용이 일부 겹친다.

## 작업 기록 (진행 순서대로)

실험 결과만 보면 과정이 보이지 않아서, 무엇을 어떤 순서로 했고 왜 그렇게 결정했는지를 남긴다. 아래 수치는 모두 당시 실제 실행 결과다.

### 0. 시작 전 결정

- **대상 문서**: 삼성전자 지속가능경영보고서 2025(87쪽). 표와 숫자가 많고, 쪽 번호가 명확해 "정답 근거 쪽"을 정의하기 좋았다.
- **평가가 주인공**이라 웹 UI·배포는 처음부터 범위에서 뺐다. 대신 `python -m rag_eval run --config ...` 한 줄로 재현되는 것을 목표로 잡았다.
- **단계 기준(M0~M4)** 을 먼저 정하고, 각 단계의 완료 기준을 통과한 뒤에만 다음으로 넘어갔다. M0 파싱 → M1 검색 → M2 평가 스크립트 → M3 실험(dev만) → M4 heldout 1회.
- 설정은 전부 `configs/*.yaml`에 두고 코드에 숫자를 박지 않기로 했다. 가중치·청크 크기 실험이 설정 파일 복사만으로 되게 하기 위해서다.

### 1. M0 — 파싱: 표가 잘리지 않는지부터 확인

**처음 결과.** PyMuPDF 본문 + pdfplumber 표 조합으로 돌리니 87쪽에서 표가 26개, 총 93행만 잡혔다. 쪽별 글자 수·표 수·표 행 수를 찍는 보고 명령(`parse`)을 만들어 보니 문제가 바로 보였다.

- 핵심 숫자 표가 모여 있는 **Facts & Figures(62~74쪽)에서 표가 0개** 검출됐다. 이 표들은 테두리 선이 없어서 pdfplumber의 선 기반 탐지에 걸리지 않았다. 텍스트 기반 탐지로 바꾸면 좌우로 나란히 놓인 두 표를 하나로 뭉개서 열이 깨졌다.
- 76~79쪽(제3자 검증 의견서)은 스캔 이미지라 텍스트가 거의 없었다. OCR은 범위 밖으로 두고 한계에 적었다.
- 선 기반으로 잡힌 26개 표 중 상당수는 1~3행짜리 박스였다.

**해결.** 단어 좌표를 직접 쓰기로 했다. 단어를 y좌표로 묶어 "줄"을 만들고, x 간격으로 "셀"을 나눈 뒤, 숫자가 2개 이상 이어진 다음 글자가 나오거나 같은 연도가 반복되면 옆 표로 분리했다. `2022년 2023년 2024년`이 있는 줄을 헤더로 삼아 값 열에 이름을 붙이고, `[계약 종류별 임직원 수]` 같은 소제목은 항목 앞에 붙였다. 각주 번호(`1)`, `임직원1)`)는 괄호 균형이 깨지지 않을 때만 지웠다. 그래야 `(Scope 1)`은 살고 `임직원1)`은 정리된다.

이 과정에서 64쪽을 눈으로 대조하며 세 번 고쳤다. 처음엔 좌우 표의 연도 헤더가 하나로 합쳐졌고(연도 반복 시 분리로 해결), 다음엔 오른쪽 표의 항목 이름이 왼쪽 표에 붙었다(열 "밴드"를 만들어 셀을 소속 밴드로 보내서 해결). 최종적으로 64쪽은 화면과 동일하게 왼쪽 26행, 오른쪽 7행, 아래 5행으로 나왔다.

**결과.** 테두리 없는 표 45개, 399행을 추가로 복원해 전체 표 행이 93 → 492가 됐다. 표 한 행은 `항목: 직접 배출량(Scope 1) | 단위: 천 톤CO₂e | 2022년: 5,972 | 2023년: 3,733 | 2024년: 4,725` 형태의 한 줄이 된다. 남은 한계는 헤더가 2단(연도 × 사업부문)인 72~74쪽으로, 숫자는 잡히지만 열 이름이 연도까지만 붙는다.

### 2. M1 — 검색: 벡터와 BM25를 각각 동작시키기

- **임베딩은 로컬 bge-m3**로 했다. 비용 0, 완전 오프라인 재현, 그리고 리랭커(bge-reranker-v2-m3)와 같은 계열이라 설명이 깔끔하다. OpenAI text-embedding-3-small로 바꾸는 건 설정 한 줄이다.
- **임베딩 캐시**를 SQLite로 두어 같은 텍스트는 두 번 계산하지 않게 했다. 재실행 시 "381 hits / 0 misses, 모델 호출 0회"를 로그로 확인했다.
- **BM25는 kiwipiepy 형태소**를 썼다. 띄어쓰기 토큰만 쓰면 "임직원이"와 "임직원"이 다른 토큰이 된다. 테스트에서 "임직원이 몇 명인가요"가 "임직원 수는 262,647명" 청크를 찾는지로 확인했다.
- **융합**은 각 검색기의 후보 50개를 min-max 정규화한 뒤 `w·vector + (1−w)·bm25`. w=0이면 BM25만, w=1이면 벡터만이라 하나의 코드 경로로 단독·하이브리드를 다 비교할 수 있다.
- 실제 문서로 돌려보니 구어체 질의("직원이 총 몇 명이야")는 BM25 점수가 낮은데 벡터가 받쳐 줬고, "재생에너지 전환율"은 벡터가 25쪽 표를, BM25가 14쪽 본문을 1위로 올려 서로 다른 답을 냈다. 이 차이가 M3에서 숫자로 드러날 부분이라고 적어 뒀다.

### 3. M2 — 평가 스크립트와 heldout 보호 장치

- 적중 기준은 "상위 k개 청크의 `page`가 `gold_pages`에 포함"으로 정했다. 청크 단위 정답 라벨은 사람이 만들기 어렵고, 쪽은 문서에서 바로 읽을 수 있기 때문이다.
- Recall@1/3/5, MRR을 전체와 type별로 계산하고, 질문별 순위·적중 여부를 CSV로 남기게 했다.
- **heldout은 `--split heldout`을 명시해야만 돌고, 돌 때 경고를 찍는다.** 가중치 일괄 실험(`sweep`)은 아예 dev만 읽는다. 실수로 heldout을 튜닝에 쓰는 일을 코드로 막았다.
- 임시 질문 5개로 요약 표·놓친 질문 목록·결과 파일 4종이 나오는지, heldout 문항이 기본 실행에 섞이지 않는지 확인한 뒤 임시 파일은 버렸다.

### 4. 평가셋 40문항: AI 초안 + 직접 검수

- **초안은 AI 도구로 만들었다.** 유형 배분·바꿔 쓰기·heldout 추출 방식은 내가 정해서 지시했고, 나온 문항을 원문과 대조해 검수했다. 검수 중 발견한 문제는 아래 "검수 기록"에 남긴다.

- **유형 배분**: number 15 / table 8 / text 12 / multi 5. 숫자·표 질문이 특히 약한지 보는 게 목적이라 숫자 쪽을 많이 넣었다.
- **질문은 문서 표현을 베끼지 않고 바꿔 썼다.** "직접 배출량(Scope 1)" 대신 "사업장에서 직접 배출한 온실가스". 문서 단어를 그대로 쓰면 BM25가 너무 쉽게 맞춰 변별력이 사라진다.
- **정답 검증 두 단계**: 모든 정답의 핵심 숫자·단어가 gold 쪽 원문에 실제로 있는지 자동 대조(40개 전부 통과), 같은 숫자가 다른 쪽에도 있으면 그 쪽을 gold에 추가(총 임직원 수는 64쪽 표 외에 5쪽 회사소개에도 있어 둘 다 gold).
- **heldout 10개(25%)는 시드 고정 무작위 추출.** 쉬운 것만 heldout에 몰리는 편향을 피하려고 사람이 고르지 않았다.
- 일부러 어려운 것도 넣었다. 재생에너지 전환율처럼 DX만·DS만·전사 수치가 다른 쪽에 따로 있는 지표, 사업부문별 표(72쪽)와 행 이름이 같은 전사 표(68쪽) 등.
- **검수 기록**: (문항별 검수 후 기재. heldout 10문항은 이미 결과를 봤으므로 질문·정답을 고치지 않고, 문제가 있으면 여기에만 적는다.)

### 5. M3 — 실험 (dev 30문항만)

- **가중치 6종**(0/0.3/0.5/0.6/0.7/1.0): BM25만 R@1 0.833, 벡터만 0.900, w=0.6~0.7에서 0.967. 예전에 비교 없이 썼던 0.6이 최적 구간(0.5~0.7) 안에 있었다.
- **리랭커 on/off**: BM25 단독에는 큰 효과(0.833 → 0.967), 하이브리드 위에서는 역효과(0.967 → 0.933). 리랭커가 표 행보다 같은 단어가 든 서술문을 선호해서 매출액 질문에서 62쪽 표 대신 5쪽 회사소개를 골랐다.
- **청크 400/800/1500자**: 1500자가 가장 좋았다(w=0.6 R@1 1.000). 한 쪽에 표 하나가 통째로 들어가는 문서라 표가 안 쪼개지는 쪽이 유리하다.
- **실패 분석 중 평가셋 결함 발견.** 1위를 놓친 질문의 상위 청크를 보니 정답이 적힌 쪽이 더 있었다(탄소중립 목표 연도는 14·22쪽 외에 4쪽 CEO 메시지와 8쪽 요약표에도 명시). 이런 gold 누락 8건을 보완하고 **36개 실행을 전부 다시 돌렸다.** 결과 절의 수치는 보완 후 값이다.
- 실패 원인 분류: 일반 용어 빈도 편향(BM25), 같은 지표의 범위별 수치 혼재, 라벨이 같은 표 혼동, 의미상 가까운 다른 쪽(벡터), 리랭커의 서술문 선호, gold 누락.

### 6. M4 — heldout 1회

확정 설정(1500자, w=0.6, 리랭커 off)으로 heldout 10문항을 한 번 돌렸다. Recall@1 0.900, Recall@3 1.000, Recall@5 1.000, MRR 0.950. 놓친 1문항은 드림클래스 누적 수혜자 수로, 소개 서술문(52쪽)이 숫자 표(63쪽)보다 위에 올랐다. dev에서 본 "서술문이 표 행을 밀어내는" 패턴 그대로였다. dev(1.000)보다 낮은 것은 dev에서 설정을 고르고 gold를 보완한 데 따른 낙관 편향으로 본다.

### 7. 사후 점검 — 지표 편향과 유의성

heldout을 쓴 뒤에는 더 튜닝하지 않았다. 대신 이미 있는 결과를 두 가지로 다시 봤다.

- **청크 안에 정답이 있는가(AnsHit@k).** 쪽 단위 지표는 큰 청크에 유리하니, "gold 쪽의 청크이면서 정답 값이 그 텍스트에 있는가"로 재채점했다. 순위는 그대로였다(1500자 Ans@1 0.967, 800자 0.933). 다만 1500자에서도 1문항은 쪽은 맞고 1위 청크엔 정답 문장이 없었다.
- **부트스트랩 신뢰구간.** 30문항을 5,000회 재표본해 보니 w=0.6과 0.7은 구분되지 않고, 1500자·벡터만·리랭커 추가도 기준(800자, w=0.6)과 유의한 차이가 없었다. 유의하게 나쁜 것은 BM25만과 BM25 위주(w=0.3)뿐이었다. 그래서 "1500자를 확정한 것은 점추정이 가장 좋아서이지 통계적으로 우월해서가 아니다"라고 결과 절에 적었다.

### 8. 하지 않은 것과 그 이유

- **OCR**(76~79쪽 스캔): 검증 의견서라 질문 대상으로서 가치가 낮고, 범위를 넓히면 평가가 주인공이라는 원칙이 흐려진다.
- **2단 헤더 표 결합**(72~74쪽): 숫자는 이미 추출되고, 쪽 단위 평가에는 영향이 없어 뒤로 미뤘다.
- **생성 단계 평가**(숫자 정답 일치율, 인용 정확도): 검색 평가를 끝까지 하는 것이 우선이었다. 다음 과제로 남긴다.
